## HIGH

### H-1. A stale overview underneath the stack can silently restart an in-progress cook

> **FIXED 2026-08-23, commit `05c91ad`** — `RecipeDetailsScreen` subscribes
> to `AppDataChanges.cookLog` and re-reads the resumable session on every
> signal. Repro covered end to end (widget test + live dev generation):
> `docs/sessions/2026-08-23_post-audit-fix.md`.

- **Class/file:** `_RecipeDetailsScreenState._loadResumableSession` /
  `_startCooking`, `lib/screens/recipe_details_screen.dart:76-120`
- **Repro:** My recipes → overview → Start cooking → advance a few steps →
  back arrow (Cook Mode `pushReplacement`s a **new** overview on top; the
  original overview State is still alive underneath) → back again (lands on
  the original overview) → Start cooking. `_resumableSession` there was loaded
  in `initState` **before the session existed** and is never refreshed — no
  `AppDataChanges.cookLog` subscription, no `didPopNext` — so this launches a
  fresh `CookModeLaunchRequest`, and Cook Mode's `saveActiveSession` **overwrites
  the in-progress session at Step 1**. Progress is silently lost; a
  planner-launched cook would also lose its `PlannerSlotRef` (fresh launch
  carries null).
- **This violates the project's own standing rule** ("a new cross-screen read
  gets a subscription to the signal for its store"): `loadActiveSession()` is
  a cross-screen read of the cook-session store, and `saveActiveSession` /
  `clearActiveSession` already fire `AppDataChanges.cookLog`.
- **Proposed fix:** subscribe `_loadResumableSession` to
  `AppDataChanges.cookLog` (held in State, cancelled in dispose), exactly like
  Home's resume banner.

### H-2. The back-from-Cook-Mode round trip stacks two overviews of the same recipe

> **FIXED 2026-08-23, commit `05c91ad`** — `_backToOverview` pops to the
> launching overview when `OverviewRouteRegistry` reports one mounted for the
> same recipe key, and replaces otherwise. Never two overviews of one recipe
> on the stack; the rule is now in `docs/DECISIONS.md`.

- **Class/file:** `_OnePanCookingRoadmapScreenState._backToOverview`,
  `lib/screens/one_pan_cooking_roadmap_screen.dart:1438`, with
  `_RecipeDetailsScreenState._startCooking` pushing Cook Mode via `context.push`.
- **Repro:** overview → Start cooking (`push`) → back arrow
  (`pushReplacement(AppRoutes.recipe)`) leaves `[…, overview(old),
  overview(new)]` — back now needs two presses to leave, through two copies of
  the same screen, the lower one stale (see H-1). The `pushReplacement` was
  chosen so a round trip "cannot stack Cook Modes"; it stacks overviews instead
  whenever the overview itself was the launcher.
- **Proposed fix:** in `_backToOverview`, `pop` when the previous route is
  already this recipe's overview (or have the overview push Cook Mode with
  `pushReplacement` so there is only ever one of the pair in the stack);
  either way H-1's subscription is still wanted.

## MEDIUM

### M-1. On the resume path, the overview's live stepper is a lie

> **FIXED 2026-08-23, commit `05c91ad`** — while a session is in progress the
> stepper renders disabled at the session's locked N
> (`RecipeOverviewBody.enabled`), re-enabling via the cookLog signal when the
> session ends.

- **Class/file:** `_RecipeDetailsScreenState._startCooking`,
  `lib/screens/recipe_details_screen.dart:103-111` +
  `RecipeOverviewBody` stepper.
- **Reasoning:** when `_resumableSession != null`, Start cooking pushes the
  stored session and **ignores the stepper entirely** (resume keeps the
  session's `currentPortions` — correct per the signed lock rule), but the
  stepper stays enabled, shows the default-precedence value rather than the
  session's, and the CTA still reads "Start cooking" with no resume
  indication. The user can set Serves 6, press the CTA, and get Serves 2.
- **Proposed fix:** when a resumable session matches, render the stepper
  read-only at `session.currentPortions` (and optionally relabel the CTA) —
  display only, no mechanics change.

### M-2. Two different null-servings fallbacks inside Cook Mode disagree

> **FIXED 2026-08-23, commit `05c91ad`** — one function,
> `resolveCookModeServings` (`lib/models/recipe_scale.dart`): launch →
> household if onboarded → `basePortions` → 1, resolved once into
> `_currentPortions` at mount; `_buildMiseCard`'s separate chain deleted.

- **Class/file:** `_OnePanCookingRoadmapScreenState._buildMiseCard`
  (`lib/screens/one_pan_cooking_roadmap_screen.dart:1874`) vs the
  `_ingredients` getter (same file, `:414`).
- **Reasoning:** with `widget.servings == null` (generation surfaces and the
  planner Cook button bypass the overview), the mise card's pill and rows
  fall back to `defaultServingsFor(profile household if onboarded → basePortions)`
  while `_ingredients` — which feeds the overview sheet's ingredients pane,
  the SOS payload, and the ledger's `cookedIngredients` — falls back to
  `_basePortions` only. Whenever household ≠ the recipe's `basePortions`
  (e.g. household changed after the recipe was generated, then cooked from
  the planner), Step 1 says "Serves 5"/500 g while the mid-cook ingredients
  pane says 200 g.
- **Proposed fix:** resolve the default once in `initState`
  (same `defaultServingsFor` precedence) into `_currentPortions` instead of
  computing two different fallbacks at render time.

### M-3. True worst case is 7 model calls per recipe, 9 per Fridge Clearer intent — documented nowhere, and the edge function 502s under bursts

> **FIXED 2026-08-23, commit `299f078`** — one client retry after 1500 ms on
> 502/503/504 (`ChefService.invokeWithGatewayRetry`, never 4xx, idempotent),
> and the worst-case counts are documented in CLAUDE.md and DECISIONS.md
> (billed calls unchanged at 7/9; HTTP requests up to 14/18). Server-side
> rate limiting remains roadmap item 19.

- **Class/file:** `generateValidatedRecipe`,
  `lib/services/validated_recipe_generation.dart` (caps: 2 compat + 2 safety +
  2 allergen) + `_generateIdeasWithAllergenFilter`,
  `lib/screens/fridge_clearer_screen.dart:259` (1 + 1 silent regenerate).
- **Reasoning:** worst case per recipe = 1 + 2 + 2 + 2 = **7 calls**
  (~7,900 prompt tokens each); a Fridge Clearer intent adds up to 2 stage-1
  calls = **9**. The safety session doc claims "worst case four" — written
  before the allergen layer landed — and the live probe already saw the
  deployed function 502 on back-to-back calls. No rate limiting exists
  (roadmap item 19).
- **Proposed fix:** document the true number (done in CLAUDE.md by this
  audit's freeze), and consider a shared retry budget across the three
  validators before real testers.

### M-4. A retry from a later validator can serve findings an earlier validator would have corrected

> **FIXED 2026-08-23, commit `299f078`** — every accepted regenerate
> re-enters the full chain from the top (compat → safety → allergen → H1
> injection last, every branch); budgets per-validator, never refunded.
> Ruling recorded in `docs/DECISIONS.md`.

- **Class/file:** `generateValidatedRecipe`,
  `lib/services/validated_recipe_generation.dart:193-251`.
- **Reasoning:** a safety-retry recipe has its compat report *recomputed but
  never re-corrected*; an allergen-retry recipe additionally gets **no safety
  correction round at all** — new H2–H11 findings introduced by an allergen
  retry are only re-detected for the log (the final `validateRecipeSafety`
  re-read) and then served. H1's injection is applied last and is safe. All
  layers fail open by design, so nothing here breaks a guarantee — but the
  interaction is undocumented and means "safety retries: 2" is not a promise
  that the served recipe went through a safety correction round.
- **Proposed fix:** document the precedence (allergen > safety > compat) as
  the intended trade; if a stricter loop is ever wanted, re-enter the safety
  loop once after an accepted allergen retry.

### M-5. Paywall sells features that no longer exist

- **Class/file:** `PaywallScreen`, `lib/screens/paywall_screen.dart:282`

### M-6. `max_tokens: 1200` headroom is thin since the declared-field additions

> **CLIENT HALF FIXED 2026-08-23, commit `299f078` — the EDGE REDEPLOY IS
> OWED.** The deployed function hardcodes 1200 (an effective clamp; the
> insurance-bundle brief's STOP clause fired — no deploys that session) and
> returns no `finish_reason`. Live proof the finding is real: an
> 8-step-traybake request measured `completion_tokens: 1200/1200`, JSON
> unclosed. The client sends `maxTokens: 2000` on both recipe surfaces and
> logs `finish_reason: "length"` to `GenerationTruncationLog` — both dormant
> until the redeploy; exact diff in
> `docs/sessions/2026-08-23_insurance-bundle.md`.

- **Class/file:** `supabase/functions/ask-chef-harris/index.ts:141`.
- **Reasoning:** real completions measured this week run 803–1,020 tokens
  (the cooking-times key, cut, cue and curriculum fields all grew output). A
  long recipe hitting 1,200 truncates mid-JSON → parse failure → user-visible
  "try again" with no signal why — invisible in logs because the function
  returns 200.
- **Proposed fix:** raise `max_tokens` to ~1,600 for `forceJsonObject` calls
  (an edge-function change: deploy explicitly, per the standing rule), or log
  `finish_reason` so truncation is at least observable.

## LOW

### L-1. The mise step's frozen bullets can show a stale scale after resume

`_buildPrepStep` (`one_pan_cooking_roadmap_screen.dart:638`) bakes
amount-bearing strings from `_ingredients` at `initState`, **before** the
resume block applies `resume.currentPortions` — so the overview sheet's step
pane (which renders step bullets) shows base-scaled amounts on a resumed,
rescaled cook. The mise **card** itself renders live from
`structuredIngredients` and is correct. Fix: build `_steps` after the resume
block, or drop amounts from the prep bullets.

### L-2. `CFBundleName` is still `dreamflow`

`ios/Runner/Info.plist:21`. `CFBundleDisplayName` was fixed to "OptiMeal dev";
`CFBundleName` (used by some system UI as a fallback) was not. Cosmetic on a
Windows-only dev setup; one-line fix whenever iOS work happens.

### L-3. The post-cook nudge relies on Home happening to rebuild

`_HomeDashboardScreenState._maybeShowPendingUpgradeNudge` is checked from
`build`; the frame that matters arrives via the async ledger/cookLog re-reads'
`setState`, which in practice lands after Cook Mode's dispose. If it ever
doesn't, the nudge is deferred (never swallowed) until the next rebuild —
acceptable, but worth knowing it is timing-dependent rather than event-driven.

### L-4. Dead back-result protocol in Cook Mode

`_backToOverview`'s demo branch returns `context.pop(_cookSequenceStarted)` —
the `push<bool>` consumer (`_openPlannedMeal`) was deleted in the planner
redesign; nothing reads the bool anymore.

### L-5. Client-side cost estimate ignores the cached rate

`ChefService._logEstimatedCost` bills all prompt tokens at the full input
rate (debug console only; the authoritative row is written server-side at the
cached rate). Overstates the console figure on warm calls by up to ~2×.

### L-6. Known-dead code still present (all previously recorded, re-verified)

- `user_profiles` `user_id` fallback query (`ai_recipe_service.dart:99`) —
  the column has never existed; `42703`, degrades gracefully.
- `YourMonthCard` and `techniqueOfTheWeek()` — mounted nowhere.
- 7 analyze warnings: 4 × `unnecessary_cast` (`ai_recipe_service.dart`),
